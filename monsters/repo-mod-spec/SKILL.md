# Спецификация и готовность монстра

1. Разбей дизайн на наблюдаемые требования. Для каждого опиши стимул, существенные настройки и ожидаемый результат. Отдельно укажи отмену, завершение фазы и состояние после смерти, оглушения, отпускания или смены уровня. Для коопа запиши владельца решения, представление клиента и структуру подтверждения урона.
2. Подбери основной, отрицательный и граничный случай. Например, «выпад достигает стоящего игрока», «закрытая створка перекрывает контакт», «тот же выпад при смене коллайдера игрока в кувырке». Для спавна укажи допустимые точки, лимит, прогрессию и поведение отказа.
3. Сделай измерения проверяемыми. Для движения запиши минимальный прогресс корпуса, точки маршрута и допустимую паузу. Для нагрузки определи область измерения, интервалы, репрезентативный стресс и базу сравнения. Для атаки задай предупреждение, подтверждённый контакт, изменение HP и выход из фазы.
4. Разложи зависимости в порядке, пригодном для тестирования. Регистрация и здоровье предшествуют полному prefab, затем обычно идут навигация, бой и сетевые сценарии. Привяжи задачи к проверкам. Проверь наличие входов, согласованного `design.md`, сведений о версиях, тестового окружения и выбранного визуального решения или обоснования, почему оно не нужно.
5. Если проект использует OpenSpec или собственную проверку готовности, выполни её из корня проекта. Отрази реальные блокеры и зафиксируй, какие результаты ещё нужно получить в игре.

Пример критерия для прохода: «На записанной раскладке погони корпус проходит все заданные точки через дверную раму штатным управлением, ни одна обязательная проверка коллизий не отключена, следующий участок маршрута доступен. Положительный контроль — тот же маршрут со свободным проходом. Закрытая запертая дверь должна сохранить блокировку».
